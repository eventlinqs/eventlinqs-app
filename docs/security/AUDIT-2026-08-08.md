## WHY A PRIVILEGE CHANGE NEEDS A READ-PATH PRE-FLIGHT

Recorded at the top permanently, at the founder's instruction, because it is the
most transferable lesson in this pass.

Migration `20260808000010` narrows column privileges. As first written it would
have **broken Stripe Connect onboarding**, which was the founder's first action the
following morning. `src/app/api/stripe/connect/onboard/route.ts:92` reads
`organisations.email` with the SESSION client, and `email` is one of the columns
the migration revokes from `authenticated`.

**Nothing that normally protects this repository could have caught it:**

- **TypeScript could not.** The column exists, the types are correct, the query
  compiles. A privilege is not part of a type.
- **1488 passing tests could not.** They run against a database where the grant has
  not changed yet. The failure does not exist until the migration is applied, and
  then it exists in production.
- **A code review could not,** realistically. The defect is not visible in either
  file alone. It lives in the pairing of a migration in `supabase/migrations/` with
  a `.select()` five directories away, and only for one of the three Postgres roles.

**And the failure mode is the loud one, which is worse here, not better.** A column
privilege failure is fail-closed by design: PostgREST returns
`permission denied for column email`. But it fails the **whole query**, not the one
field, so the page does not degrade, it breaks. Fail-closed is the right security
posture and it is still an outage.

**The general rule, now enforced by
`scripts/security/revoked-column-reads.mjs` (registered in `run-guards.mjs`):**

> A change to column privileges is a change to every read path that touches those
> columns. Before applying one, enumerate every query against the affected tables,
> resolve which Postgres role each one runs as, and confirm none of them asks for a
> column it will no longer have.

The guard resolves the client **per query**, not per file, because a file-level
guess reported 25 hits of which most were reads already moved to the service role,
and an over-report nobody can act on is the same as no report. It found five real
breakages: Connect onboard, refresh and return, plus both founding-invites
surfaces. It also found the opposite mistake, where I had over-restricted
`seats.note`, which a ticket holder legitimately reads.

The same reasoning applies to any privilege or policy change, not just this one:
`REVOKE`, `DROP POLICY`, a role change, a view swap. The write path is what gets
reviewed; the read paths are what break.

## PROVENANCE, and it decides how much any claim below is worth

Founder-supplied `pg_policies` output on 2026-08-08 checked four tables against
production and found this audit **right on two and wrong on two**. That is the
most useful thing that happened in this pass, so it is at the top.

Every finding is now labelled with where its evidence came from:

| Label | Meaning |
|---|---|
| **LIVE-VERIFIED** | Confirmed against production `pg_policies`. Evidence. |
| **CODE-VERIFIED** | Confirmed by reading source that runs, or by executing it. Evidence. |
| **MIGRATION-DERIVED** | Inferred from migration files. **A hypothesis, not evidence.** |

A migration is what somebody **intended**. `pg_policies` is what the database
**does**. They diverge whenever a migration was never applied, was applied out of
order, was hand-edited in a console, or was superseded by a later `DROP` a grep
did not see. `scripts/security/rls-live-audit.sql` exists so no policy claim has
to be MIGRATION-DERIVED again; it must be run before this report is trusted on
any table not already marked LIVE-VERIFIED.

**Corrections forced by the live check:**

- **`profiles` is SAFE. There is no CRITICAL-0.** The `20260625000002` lockdown
  DID reach production and the only SELECT policy is `USING (auth.uid() = id)`.
  I had left this open as a question I could not answer from here. It is now
  closed. **No user emails or phones are world-readable.**
- **`squads` is SAFE and `share_token` is NOT world-readable.** The live policy
  is scoped to the leader or a member. My original claim was wrong. I had already
  withdrawn it before the live check (see the retraction below, committed in
  `14d4a88`) because replaying the migrations in order found the `DROP`, but the
  live catalogue is what settles it.
- **`seats` is CONFIRMED EXPOSED and I had wrongly deferred it as LOW.** I
  reasoned that a user UUID is not a contact detail. That was too narrow: `USING
  (true)` on `seats` lets an anonymous caller map `held_by_user_id` to work out
  **who is sitting where at any event**. It is now fixed in the same migration.
- **CRITICAL-1 is two tables, not three.** `organisations` and `seats`. Smaller
  than I first reported, and accurate.

**What this means for the rest of the document.** `event_artists` (HIGH-1) and
`venues` are **MIGRATION-DERIVED and NOT live-verified**. HIGH-1's severity rests
on a policy I have not seen in the catalogue. The `lineup.ts` half of it, that the

## RETRACTION, recorded before anything else

My first write-up of CRITICAL-1 claimed that **every squad share token** was
world-readable. **That claim is wrong and is withdrawn.**

`supabase/migrations/20260520000001_schema_hygiene.sql:426` drops the policy, and
says why in its own comment:

```sql
-- Guest share-token squad reads are performed server-side via
-- the service role ("Service role manages squads", unchanged),
-- so removing the blanket public policy closes the "any anon
-- can read every squad" hole without breaking the share-link
-- join flow.
DROP POLICY IF EXISTS "Squads are viewable by anyone with the share token" ON public.squads;
```

The cause of my error: I found the policies with `grep`, which reads
`CREATE POLICY` and cannot see a later `DROP POLICY`. A migration set has to be
**replayed in order** to know the live state. The scanner below does that, which
is how it caught me.

The `organisations` finding is unaffected and is confirmed, wider than I first
reported (11 sensitive columns, not 5). A second real finding, on
`event_artists`, was found by the scanner and not by the grep. Net: the headline
severity is unchanged, one sub-claim was false, and one new one is real.

## The complete world-readable inventory, by replay

`scripts/security/rls-exposure-scan.mjs` replays all 77 migrations in
chronological order, honours `DROP POLICY`, reconstructs each table's columns
including `ALTER TABLE ADD COLUMN`, and reports every world-readable SELECT
policy that meets a sensitive column. Result: **156 live policies over 75
tables; 28 are world-readable; 12 of those expose a sensitive column.**

A policy counts as world-readable only when it is PERMISSIVE, covers SELECT,
reaches `anon` (no `TO` clause means PUBLIC), **and** its `USING` expression does
not pivot on caller identity. That last clause matters: an uncorrected first pass
reported 33 tables because it counted
`USING (auth.role() = 'service_role')` policies, which have no `TO` clause but
can never match `anon`. Conflating those with the real thing would have turned a
2-table problem into a 33-table panic.

| Table | Policy `USING` | Sensitive columns exposed | Rank |
|---|---|---|---|
| `organisations` | `status = 'active'` | `email`, `phone`, `owner_id`, `metadata`, `stripe_account_id`, `stripe_account_country`, `stripe_charges_enabled`, `stripe_payouts_enabled`, `stripe_onboarding_complete`, `stripe_capabilities`, `stripe_requirements` | **CRITICAL** |
| `event_artists` | `true` | **`invite_token`** (single-use profile-claim credential) | **HIGH** |
| `venues` | `is_active = true` | `address`, `stripe_account_id`, `stripe_account_country`, `stripe_payouts_enabled` | MEDIUM |
| `events` (x2 policies) | `status='published' AND visibility='public'` / `'unlisted'` | `metadata`, `created_by` | MEDIUM |
| `ticket_tiers` | visible+active on published events | `metadata` | MEDIUM |
| `seats` | `true` | `held_by_user_id`, `metadata` | LOW |
| `artists` | `true` | `owner_user_id` | LOW |
| `gigs` | `status = 'open'` | `created_by` | LOW |
| `pricing_rules` | `organisation_id IS NULL` | `created_by` | LOW |
| `seat_section_views` | `true` | `created_by` | LOW |
| `feature_flags` | `true` | `updated_by` | LOW |

The 16 world-readable tables with no sensitive column are genuinely public
reference data and are correct as they stand: `cities`, `communities`,
`cultures`, `event_categories`, `event_types`, `genres`, `subgenres`, `suburbs`,
`seat_maps`, `seat_map_sections`, `event_addons`, `dynamic_pricing_rules`,
`tax_rules`, `refund_tickets`, and two `storage.objects` buckets.

**One limit on this inventory, stated plainly.** It describes the schema the
repository *intends*. It cannot see which migrations were actually applied to
production. If a migration never ran there, production is more exposed than this
table says, never less. That is exactly why the `profiles` question is open: the
scanner correctly shows `profiles` as closed because `20260625000002` drops the
policy in the repo, and that tells us nothing about whether it reached
production.

**Incidental, not a security finding:** the live schema still has a `cultures`
table. CLAUDE.md bans that word in database tables and columns, so it is a
constitutional defect. Out of scope for this pass; flagged, not touched.

## HIGH-1: every unclaimed artist invite token is world-readable, and the token
## hands over ownership of an artist profile

**ASVS 8.2.3** (field-level authorisation / BOPLA), **ASVS 8.3.1**
(authorisation must not rely on a control an untrusted consumer can bypass),
**ASVS 6.4.1** (activation codes must expire and not become long-term
credentials).

`supabase/migrations/20260530000003_event_artists.sql`

```sql
CREATE POLICY "event_artists_public_read" ON public.event_artists
  FOR SELECT USING (true);
```

`event_artists.invite_token` is in that table. What the token does
(`src/app/actions/lineup.ts:247-262`):

```ts
const { data: tag } = await admin.from('event_artists')
  .select('id, artist_id, event_id').eq('invite_token', token).maybeSingle()
if (!tag) return { ok: false, error: 'This invite link is not valid or was already used.' }

await admin.from('event_artists').update({ status: 'confirmed', invite_token: null }).eq('id', tag.id)

// Hand the profile to the claimer only when unowned
await admin.from('artists').update({ owner_user_id: user.id })
  .eq('id', tag.artist_id).is('owner_user_id', null)
```

So the token confirms a lineup tag and **transfers ownership of the artist
profile to whoever presents it**, for any profile not already owned.

Reading the tokens needs nothing at all: they are a column on a world-readable
table, fetched with the public anon key. Redeeming one needs a free account,
because the action calls `getUser()`. So the attack is: list every
`invite_token` on the platform, sign up, then claim every unowned artist profile,
taking control of those public profile pages and their artist dashboard.

The token itself is well made (a UUID, single-use, nulled on redemption, and the
claim refuses an already-owned profile). None of that helps when the credential
is published. This is ASVS 8.3.1 again: the check is sound and the attacker never
has to face it.

Gated behind the `broadcast_artists` flag, which is ON for launch.

## CRITICAL-1: every active organiser's contact details are readable by an
## anonymous stranger through the public anon key

**ASVS 8.2.3** (field-level access must be restricted to consumers with explicit
permissions, to mitigate broken object property level authorisation / BOPLA).
Also **ASVS 8.2.2** (data-specific access), **ASVS 1.2.2** equivalent intent in
V14 Data Protection, and **ASVS 8.3.1** (authorisation enforced at a trusted
service layer, not by a control an untrusted consumer can bypass).

**Severity: CRITICAL. Live on production. No account, no session, no tooling
beyond a browser.**

### The defect

Row Level Security filters **rows**, not **columns**. Three tables carry a
world-readable SELECT policy, and no column privileges anywhere restrain what
those policies expose.

`supabase/migrations/20260101000001_baseline_schema.sql:88`

```sql
CREATE POLICY "Organisations are viewable by everyone"
  ON public.organisations FOR SELECT
  USING (status = 'active');
```

The columns that policy hands out (`baseline_schema.sql:61-75`):

```
id, name, slug, description, logo_url, website,
email,                        <-- organiser contact email
phone,                        <-- organiser contact phone
status,
owner_id,                     <-- the auth.users UUID behind the organisation
stripe_account_id,            <-- Stripe Connect account identifier
stripe_onboarding_complete,
metadata JSONB,               <-- arbitrary contents
created_at, updated_at
```

Eleven of the table's 34 columns are sensitive. The full per-table inventory,
including the ten other tables in the same shape, is in the replay table above.
The credential-exposure member of this family is `event_artists.invite_token`,
written up as HIGH-1.

### Why it is reachable by a stranger, proven from source

Four facts, each independently checkable, none of them requiring me to touch
production:

1. **The policies grant SELECT to everyone**, not to `authenticated`. There is no
   `TO` clause, so they apply to `anon`. Quoted above.

2. **No column privileges restrain them.** Every `GRANT`/`REVOKE` across all 77
   migrations is on a FUNCTION, never a table column:

   ```
   $ grep -rniE '^\s*(REVOKE|GRANT)' supabase/migrations/*.sql
   ... GRANT EXECUTE ON FUNCTION public.create_reservation TO authenticated;
   ... GRANT EXECUTE ON FUNCTION public.confirm_order TO service_role;
   ... REVOKE ALL ON FUNCTION public.reconcile_refund(...) FROM PUBLIC;
   (every hit is ON FUNCTION; no table/column GRANT or REVOKE exists)
   ```

   Supabase's default grants give `anon` and `authenticated` SELECT on all
   columns of public-schema tables. Nothing here narrows that, so `select=*`
   returns every column of every row the policy admits.

3. **The anon key is public by construction.** It is
   `NEXT_PUBLIC_SUPABASE_ANON_KEY`, shipped into the browser bundle of every
   page. Anyone can read it from view-source. It is not a secret and is not
   meant to be one; RLS is supposed to be what makes that safe.

4. **The identical defect on this exact table set was already confirmed real and
   treated as a P0.** `supabase/migrations/20260625000002_profiles_rls_lockdown.sql`
   fixed the same shape on `profiles` and its own header describes the mechanism
   and the exploit path in the first person:

   > `public.profiles` holds email (NOT NULL), full_name and phone. It shipped
   > with the policy "Public profiles are viewable by everyone" FOR SELECT USING
   > (true) (baseline 20260101000001). RLS combines policies with OR, so that one
   > policy made the ENTIRE table world-readable through the public anon key,
   > e.g. `GET /rest/v1/profiles?select=email,phone` would dump every user's
   > email and phone. That is a mass-PII exposure.

   That migration dropped one policy on one table and left the same shape on
   `organisations`, `squads` and `seats` untouched. The precedent settles the
   question of whether this is exploitable: the founder already accepted that it
   is, for the sibling table, and fixed it.

**No exploit was run against production.** Reachability is established from the
policy text, the absence of column privileges, the public nature of the anon
key, and the accepted precedent. Per the brief, I proved reachability and
stopped. A one-line read-only confirmation the founder can run themselves is in
the founder action block.

### What an attacker gets

- **Every active organiser's email and phone, in bulk.** The organiser list is
  the supply side of the marketplace, the hardest-won asset in the business. A
  competitor can harvest the entire recruited organiser base as a ready-made
  contact list, and a phisher gets a target list of people who are expecting
  EventLinqs emails about money.
- **Organisation-to-user mapping** (`owner_id`), which de-anonymises who runs
  which organisation.
- **The full Stripe Connect posture of every organiser**: whether charges are
  enabled, whether payouts are enabled, the account country, and the outstanding
  `stripe_requirements`. That is a map of which organisers are not yet able to
  take money, which is commercially useful to a competitor and useful to a
  social engineer ("your payouts are blocked, verify here").
- `stripe_account_id`. On its own an `acct_...` identifier is not a credential
  and cannot move money without API keys, so I am **not** claiming payout theft
  here. It is payout infrastructure metadata and it should not be public, but the
  real harm in this finding is the bulk PII and the tokens.

Australian Privacy Act exposure is direct: a mass release of contact details is
the notifiable-breach shape, and it is the second time this class has appeared in
this schema.

### Confirmed findings, not yet written up in full

**HIGH: `/admin/login` leaks the founder's admin password, TOTP code and
recovery code on a pre-hydration submit.** ASVS 6.2.6 / 3.4.5 / 16.3.x. Identical
class to the `/login?password=` defect. `src/app/admin/login/login-form.tsx:41`
is `<form onSubmit={onSubmit}>` with no `action`, carrying `name="email"`,
`name="password"`, and `name="totp"` or `name="recovery"`. The sibling branch's
guard (`tests/unit/auth/no-native-submit.test.ts` on `fix/production-sweep`)
walks `src/components/auth` only, so this file and
`src/app/admin/(authed)/enrol-2fa/enrol-form.tsx` are outside it, as are the
non-auth forms carrying access codes and ticket codes. Ranked below CRITICAL-1
because it needs the admin to submit in the pre-hydration window, whereas
CRITICAL-1 needs nothing from anybody.

**HIGH: `next@16.2.7` is in the affected range for an App Router proxy bypass.**
GHSA-6gpp-xcg3-4w24, affected `>=16.0.0 <16.2.11`, and this project builds with
Turbopack. `src/proxy.ts` carries four security decisions (host canonicalisation,
the `/dev/*` production gate, the queue admission gate, session refresh), so a
proxy bypass defeats all four at once. Fix is `16.2.11` or `16.3.0`, not a major
bump. Eight further advisories in the same package are fixed by the same bump.

**HIGH: the rate limiter fails open on a transient store error, including for
every policy marked `failClosed`.** ASVS 2.4.1 / 6.3.1.
`src/lib/redis/rate-limit.ts:64-67` returns `ok: true` in the `catch`,
unconditionally. `failClosed` is only honoured for *missing configuration*
(line 41), never for an error. So login, signup, password reset, magic link,
checkout and AI spend all degrade to unlimited when the store errors, which is
the state an attacker would try to induce (for example by exhausting the Upstash
request quota). A control that fails open is not a control.

**MEDIUM: CSP is report-only, so it currently blocks nothing.** ASVS 3.4.3.
`next.config.ts:39` sets `Content-Security-Policy-Report-Only`. The policy also
carries `script-src 'unsafe-inline' 'unsafe-eval'`, so it would not stop
injected script even once enforced. HSTS, nosniff, frame-ancestors,
Referrer-Policy and Permissions-Policy are all present and correct.

**MEDIUM: `sharp` is a devDependency but imported at runtime, and carries libvips
CVEs reachable from attacker-supplied image bytes.** `sharp <0.35.0`,
GHSA-f88m-g3jw-g9cj. Reached via `await import('sharp')` in
`src/app/api/organiser/events/[id]/poster/route.ts:37` and the upload pipeline,
both of which process uploaded images. Genuinely reachable, unlike most of the
35 advisories.

**MEDIUM: the shared Redis store has no environment namespace, so the incident
that already happened can happen again in any of three key spaces.**
`src/lib/flags/broadcast.ts:65` is still `ff:v1:${flag}` on this branch;
`src/lib/redis/rate-limit.ts:49` is `rl:${key}:${window}`; the inventory cache is
the third. **Direct answer to the brief's question**: no code path falls back to
production. `getRedisClient()` (`src/lib/redis/client.ts`) reads
`UPSTASH_REDIS_REST_URL`/`_TOKEN` straight from `process.env` with no environment
binding and no assertion that the instance it reached matches the runtime it is
in, unlike Supabase which has real `*_PREVIEW` overrides in
`src/lib/supabase/env.ts`. So the credentials only arrive if a developer's
`.env.local` contains production values, and the known footgun is exactly that.
The real defect is therefore twofold: unnamespaced keys make any credential
mix-up silent, and there is no environment assertion to catch it. Namespacing one
key fixed one symptom and left the shape intact.

### Verified as sound, so recorded and not re-litigated

- **Cron authorisation fails closed** correctly, `src/lib/cron/auth.ts:24`,
  including when `CRON_SECRET` is unset.
- **The Stripe webhook** verifies the signature before anything else, dedupes at
  event level via `claimWebhookEvent`, and returns 500 to force redelivery on a
  retryable failure. The proxy's exemption of this path is correct, since Stripe
  does not follow redirects.
- **`getOrganiserEvent()`** (`src/lib/reporting/attendees.ts:43`) is a real
  ownership gate: session client, `owner_id = auth.uid()`, fails closed on every
  miss. `resolveOrganiserScope()` is equivalent for payouts.
- **Ticket transfer and door scan** delegate authorisation to `SECURITY DEFINER`
  RPCs rather than trusting the caller.
- **The admin console** is gated at the route-group layout
  (`src/app/admin/(authed)/layout.tsx`), so the ~17 `src/lib/admin/*`
  service-role modules sit behind one enforced check.
- **Open redirect on admin login** is not present: `next` is constrained with
  `startsWith('/admin')`.

### Considered and rejected, so they are not padding the report

- **Ticket QR brute force.** `tickets.secret` is `gen_random_uuid()`
  (`20260517000001_ticketing_system_v1.sql:52`), 122 bits from a CSPRNG. The
  route has no rate limit, but enumeration is infeasible, so this is not a
  finding.
- **`x-forwarded-for` spoofing defeating every rate limit.** It would have been
  serious. Vercel's request-headers documentation states the platform overwrites
  the header and does not forward external values, so the limiter's key is
  trustworthy. Closed, not a finding. The `x-real-ip` fallback in
  `clientIp()` is unreachable in production for the same reason.
- **Non-constant-time comparisons** on the cron bearer and the ticket secret.
