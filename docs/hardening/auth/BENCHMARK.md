# Benchmark then surpass: standard says X, we now do Y, Y is stronger because Z

Matching the published standard is the floor. For each area, the standard is
recorded, then the way we go past it: by converting the rule into automated
enforcement that fails a build or a scheduled check, so the defect cannot
silently return.

| # | Area | Standard says X | We now do Y | Y is stronger because Z |
|---|---|---|---|---|
| 1 | Auth error messages | OWASP Authentication Cheat Sheet: "an application must respond with a generic error message regardless of whether: The user ID or password was incorrect. The account does not exist. The account is locked or disabled." | One copy deck, `src/lib/auth/auth-errors.ts`, is the only path to a user-visible auth sentence. `classifyAuthError()` maps every provider code to a fixed class; no component may render `error.message`. | The standard tells you what to write. Ours makes writing anything else impossible to do by accident: 6 raw `error.message` render sites were removed, and `tests/unit/auth/auth-errors.test.ts` asserts no message can contain the words supabase, gotrue, smtp, resend, postgres, jwt, token_hash, a competitor name, an em dash or an exclamation mark. A guideline you can forget becomes a test that fails. |
| 2 | Password reset enumeration | OWASP: the response must be "If that email address is in our database, we will send you an email to reset your password", identical whether or not the account exists. | `/api/auth/recover` returns a byte-identical 200 for `sent` and `no_account`, asserted at the response-body level. | Two things past the standard. First, OWASP names only the wording; we also close the **timing** channel it warns about ("a time-based attack") with a 900ms response floor, because `no_account` short-circuits before any mail I/O and would otherwise be instantly distinguishable. Second, the same contract is applied to the magic-link and resend-verification endpoints, which OWASP does not mention and which were the more dangerous oracles: an unguarded resend endpoint answers "does this address have an unconfirmed account" for any address on request. |
| 3 | Account-existence discrepancy in code | OWASP describes the goal but leaves detection to review. | The absent-account decision is keyed on GoTrue's structured `status`, and **any unrecognised 4xx defaults to the enumeration-safe side**. | The standard cannot stop the specific bug we shipped: an earlier version matched `error.message` substrings, GoTrue answers `"User with this email not found"`, the list checked for `"user not found"`, and the mismatch produced a 502-vs-200 oracle. Defaulting all 4xx to safe means a future GoTrue wording change or new error code cannot reopen it. Locked by `tests/unit/auth/dispatch-auth-link.test.ts`. |
| 4 | Credential manager | WHATWG HTML defines `current-password` as "the current password for the account identified by **the username field**". Chromium guidance: use `autocomplete="username"`, a stable `name` or `id`, a real `<form>` with a submit button. | All five auth forms match the contract, including a hidden `autocomplete="username"` field on the reset form per Chromium's change-password guidance. | Both documents are advice. We made the contract executable at three levels: `scripts/guards/auth-autocomplete-guard.mjs` fails the **build** on the source, `tests/unit/auth/autocomplete-contract.test.ts` fails the **test suite**, and `scripts/verify/auth-credential-manager-proof.mjs` asserts the **live DOM in real Chrome** using the browser's own parsed IDL values, which proves the attributes survive React, the build, SSR and hydration. Source-level checks alone cannot prove that. |
| 5 | Supabase email limits | Supabase docs: "2 emails per hour with the built-in email provider... You can only change this with a custom SMTP setup." | All four auth emails are minted with `generateLink` (which sends nothing) and dispatched through our own Resend transport. Supabase's mailer is not in any EventLinqs auth path. | The documented remedy is a dashboard toggle. A toggle is invisible to CI, uncovered by tests, and silently revertible: it is precisely the class of configuration state that caused all three defects here. Owning the transport removes the dependency, and `scripts/guards/no-supabase-smtp.mjs` fails the build if any of the four banned calls returns. Custom SMTP is still recommended in the founder block as belt and braces for flows we do not drive. |
| 6 | Supabase provider configuration | Supabase docs: enable the provider in the dashboard before using it. | A server-resolved, fail-safe gate reads `GET /auth/v1/settings` and renders the button only if the provider is genuinely enabled; the sentinel asserts parity every 10 minutes in production. | The docs assume you will not ship a button for a provider you have not enabled. We did exactly that, and it reached production. The gate makes the wrong state unrenderable, the guard makes an ungated button unbuildable (5 checks), and the sentinel makes a silently-disabled provider alert within 10 minutes. Three layers where the standard has none. |
| 7 | Supabase redirect allowlist | Supabase docs: add every redirect URL to the allowlist; unlisted URLs fall back to the Site URL. | The sentinel probes `/auth/v1/verify` with a deliberately invalid token for each redirect URL the code builds, and reads GoTrue's own answer back. | The allowlist is normally write-only: you can set it but not read it without a Management API token. The invalid-token probe turns it into a **readable** setting with no side effects, no email and no write, so drift between the dashboard and the code becomes a monitored condition rather than a discovery during an incident. It is also how the wrong Site URL was found. |
| 8 | Google OAuth client config | Google Identity docs: the redirect URI "must exactly match one of the authorized redirect URIs... the `http` or `https` scheme, case, and trailing slash must all match." | The founder block gives the exact URI derived from the resolved project ref, plus the origins read from the code. | The standard states the rule; the previous internal setup doc violated it anyway, naming `https://eventlinqs.com` origins and `/privacy` and `/terms` legal paths that do not exist in this codebase (they are `/legal/privacy` and `/legal/terms`). Every value in the new block is read out of the running code or probed from the live system, and the one value I could not derive (Resend's SMTP host and port) is explicitly marked UNVERIFIED rather than guessed. |
| 9 | Errors reaching the browser | No published standard covers "a third-party origin returned JSON into your user's tab". | Every failure lands on a rendered EventLinqs page. `AuthErrorFromUrl` reads the query string **and the fragment**; the sentinel asserts every auth route answers a browser with `text/html`. | The fragment half is the part nobody covers and the part that was broken: GoTrue reports a dead reset link as `#error=access_denied&error_code=otp_expired`, a fragment is never transmitted to the server, so the page sat on "Validating your reset link" forever. Reading both channels, plus a content-type assertion in production, closes a gap the standards do not name. |
| 10 | Guards themselves | No standard requires proving a guard can fail. | `scripts/verify/guard-failure-drills.mjs` introduces all 10 real regressions, asserts each guard exits non-zero **for the expected reason**, and restores the tree. | "A guard never seen to fail is not a guard." The harness is repeatable and committed, not a one-off demonstration in a session nobody can replay, and it caught two of its own drills silently reporting STALE because of CRLF anchors, which is the same failure mode it exists to prevent. |
